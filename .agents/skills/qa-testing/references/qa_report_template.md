## 2. 測試計畫摘要 (Test Plan Summary)
> 於執行測試**之前**填寫，執行後不得為配合結果而回改；若計畫中途調整，須在此註明調整內容與原因。

* **測試範圍 (In Scope)**：本次驗證的功能、模組與介面（如 CLI 新參數、資料寫入路徑）。
* **不測範圍 (Out of Scope)**：刻意不測的項目與理由，以區分「決定不測」與「漏測」。

  | 不測項目 | 理由 | 風險與替代保障 |
  | :--- | :--- | :--- |
  | 例：真實外部 API 429 | 無法穩定觸發真實配額耗盡 | 由單元測試 Mock 故障注入覆蓋 (`tests/unit/test_xxx.py`) |

* **進入條件 (Entry Criteria)**：Step 3 單元測試全數通過、相依服務（資料庫、外部 API 等）就緒、測試資料備妥。
* **退出條件 (Exit Criteria)**：見第 8 節放行標準。
* **風險與優先順序**：列出本次變更風險最高的 1–3 個面向（如併發寫入、向下相容），並說明對應案例的優先級。

## 3. PRD 需求驗收追溯矩陣 (Requirements Traceability Matrix, RTM)
驗證 PRD 中的每一項 Acceptance Criteria (AC) 是否達到 **100% 測試覆蓋**：

> **Bug 軌／Hotfix**：RTM 對象改為缺陷報告第 5 節的缺陷驗收條件（`BC-1`…），加上受影響功能原規格中相關的 AC；第 2 節測試計畫只涵蓋受影響範圍。Hotfix 合併前可先以冒煙測試出具報告，補件時改為完整版。

| PRD 驗收條款 (AC) | 條款說明 | 覆蓋測試案例 (TC ID) | 測試類型 | 狀態 |
| :--- | :--- | :--- | :---: | :---: |
| **AC 1.1** | 正向資料匯入與寫入 | `TC-01` | E2E | **PASS** |
| **AC 1.2** | 既有 CLI 參數向下相容性 | `TC-02` | CLI | **PASS** |
| **AC 2.1** | 0-byte 空檔案與壞檔防禦 | `TC-03` | Edge / Fault | **PASS** |
| **AC 2.2** | 重複匯入之冪等清理 | `TC-04` | Idempotency | **PASS** |
| **AC 3.1** | 外部 API 429 速率超標降級 | `TC-05` | Circuit Breaker | **PASS** |

**狀態定義**：

| 狀態 | 意義 | 是否可放行 |
| :--- | :--- | :---: |
| **PASS** | 有對應案例且全數通過 | 可 |
| **FAIL** | 有對應案例但至少一個失敗 | 否，打回 Step 6 |
| **DEFERRED** | 延後驗證；須於下方註明理由、替代保障與核准人（人類） | 經人類核准始可 |
| **NOT COVERED** | 無任何對應案例 | 否，須補案例 |

> **RTM 統計**：PASS `N` / FAIL `N` / DEFERRED `N` / NOT COVERED `N`（共 `N` 條 AC）
>
> **DEFERRED 明細**（無則填「無」）：`AC x.x` — 理由：… / 替代保障：… / 核准：使用者於 YYYY-MM-DD 確認

## 6. 品質評測結果 (Quality Evaluation)
> 規格宣告 `品質評測範圍：是` 時**必填**；宣告為「否」者填「不適用（規格宣告品質評測範圍：否）」。操作細節見 quality-evaluation 技能（`.agents/skills/quality-evaluation/SKILL.md`）。

* **評測資料集**：`tests/eval/data/<dataset>`（合成資料，筆數 `N`）
* **評測指令**：`python -m tests.eval.<runner> ...`
* **Rubric / 評審 Prompt 版本**：`<版本或 commit>`（若本次有變更，註明原因；變更後不得與舊分數直接比較）

| 指標 | 品質 AC 門檻 | 變更前 | 變更後 | 差異 | 判定 |
| :--- | :---: | :---: | :---: | :---: | :---: |
| Recall@5 | ≥ 0.80 | 0.82 | 0.86 | +0.04 | **PASS** |
| 欄位 F1 | ≥ 0.90 | 0.91 | 0.93 | +0.02 | **PASS** |

* **Token 消耗**：輸入 `N` / 輸出 `N` tokens（評審模型與被測模型分列）；與上次評測相比 `±N%`。

## 7. 失敗分析與根因定位 (Failure Analysis & RCA)
> *若測試 100% 通過，本節填寫「無失敗項目」。若有失敗，AI 必須嚴格執行以下 RCA 分析並回饋 Step 6：*

* **失敗現象 (Symptom)**：測試名稱、報錯資訊與行號。
* **根因定位 (Root Cause)**：分析是由於介面變更、例外鏈遺漏、檔案控制代碼未釋放、還是資料寫入競態引發。
* **修復建言與回饋 (Remediation)**：具體應修改的檔案路徑與方法邏輯。

## 8. QA 驗收結論 (QA Sign-Off)
* **驗收判定**：**【通過 (PASSED)】** / **【未通過 (FAILED - 打回修正)】**
* **放行標準**（全部成立才可判定通過）：
  1. RTM 零 `FAIL`、零 `NOT COVERED`；`DEFERRED` 皆有理由、替代保障與人類核准紀錄
  2. 邊界與異常對抗實測：**全數通過 (無崩潰或未受控例外)**
  3. 資源生命週期：**驗證通過 (無控制代碼殘留與鎖定錯誤)**
  4. 品質評測（若適用）：所有品質 AC 達門檻；分數下降項已說明並標註待 Gate 2 核准
* **放行說明**：**准予放行進入 Gate 2 代碼審查！** / 打回 Step 6，待修項目：…
