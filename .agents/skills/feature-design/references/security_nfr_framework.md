# 安全與非功能需求評估框架 (Security & NFR Assessment Framework)

> **定位**：閉環**通用核心**，適用任何專案；移植時**不得刪除或改寫為專案實例**（`verify_doc_sync.py` 檢查本檔存在）。專案差異只透過 `.agents/project.toml` 的 `[security]` 特徵宣告。
> **使用時機**：feature-design 技能「安全與非功能需求評估」階段（Gate 1）；Gate 2、QA 與缺陷逃逸分析引用本檔判定。

本框架用**方法推導**問題，而不是用清單回想問題：清單只能涵蓋寫的人想得到的項目，方法換一個專案仍然有效。

---

## 一、範圍宣告

每份規格於驗收標準段落宣告：

```text
安全評估範圍：是
```

符合下列**任一**項即為「是」，否則為「否」並附一句理由：

1. 新增或變更對外介面（Web 端點、API、網路服務、檔案或訊息輸入點；CLI 參數本身除外）。
2. 新增跨越信任邊界的資料流（見第三節第 1 步）。
3. 新增外部相依服務或第三方套件。
4. 新增敏感資料（個資、憑證、商業機密）的儲存、傳輸或記錄。
5. 變更身分驗證、授權、工作階段或網路暴露範圍。

輕量變更（Fast Track）也要書面宣告，不得只做心智自檢；宣告為「是」時，第三節的威脅表可只列受影響的邊界。

---

## 二、非功能需求宣告（ISO/IEC 25010:2023 產品品質模型）

功能適合性由功能 AC 涵蓋；其餘 8 項品質特性逐項宣告：

| 品質特性 | 宣告 | 理由或對應驗收條件 |
| :--- | :---: | :--- |
| 效能效率（時間行為、資源使用、容量） | 適用／不適用 | |
| 相容性（共存、互通） | | |
| 互動能力（易學、操作、錯誤防護、無障礙） | | |
| 可靠性（成熟、可用、容錯、可回復） | | |
| 安全性（機密、完整、不可否認、可究責、真實、抗性） | | 由第三節威脅建模產出 |
| 可維護性（模組化、可重用、可分析、可修改、可測試） | | |
| 彈性（適應、擴縮、可安裝、可替換） | | |
| 安全防護 safety（操作限制、風險識別、失效安全、危害警示） | | |

規則：

* **適用**者至少一條可驗證的 `NFR-*` 驗收條件（量化門檻或可觀察結果），並列入 QA 的 RTM。
* **不適用**者寫一句理由；不得留白。
* 規格中任何敘述性的品質或安全要求（例如「只對本機開放」「回應要快」），一律改寫為 `NFR-*`，否則 Gate 1 不通過。

## 三、威脅建模（STRIDE 精簡版）

**第 1 步：畫邊界。** 列出本次變更涉及的元件、資料存放處與外部實體，標出**信任邊界**：資料從「信任程度不同」的一方流向另一方之處。常見邊界：

* 使用者端（瀏覽器、CLI 使用者、其他程式）↔ 本系統服務
* 本系統 ↔ 外部 API、雲端服務、LLM
* 不受信任的輸入內容（上傳檔案、外部文件、使用者文字）↔ 解析或處理元件
* 本系統 ↔ 資料庫、快取、檔案系統
* 本機 ↔ 網路（綁定位址、對外連接埠）

**第 2 步：逐邊界問六問。** 對每條跨越信任邊界的資料流：

| 類別 | 問題 | 對應安全屬性 |
| :---: | :--- | :--- |
| **S** 冒充 | 對方能否假冒合法的使用者、服務、來源網站或主機名稱？ | 真實性 |
| **T** 竄改 | 傳輸或儲存中的資料、設定、檔案能否被修改？ | 完整性 |
| **R** 否認 | 發生問題時，能否追查是誰在何時做了什麼？ | 不可否認、可究責 |
| **I** 資訊洩漏 | 回應、錯誤訊息、日誌、跨來源讀取、快取，會不會讓不該看到的人看到資料？ | 機密性 |
| **D** 阻斷服務 | 大量請求、超大輸入、昂貴操作（含付費 API）能否耗盡資源或費用？ | 可用性 |
| **E** 權限提升 | 能否執行超出授權的操作、讀寫超出範圍的檔案、讓 LLM 執行非預期指令？ | 授權 |

**第 3 步：記錄。**

| 邊界／資料流 | STRIDE | 威脅 | 緩解措施（引用標準條目） | 對應 NFR／測試 | 殘餘風險與嚴重度 |
| :--- | :---: | :--- | :--- | :--- | :--- |
| 例：瀏覽器 ↔ Web 服務 | I | 外站網頁跨來源讀取 API 回應 | 不開放跨來源許可（ASVS V3） | `NFR-1`、`TC-xx` | 無 |

**第 4 步：處置。** 每一列都要有緩解措施並對應 `NFR-*` 或測試案例；不處理者列為殘餘風險，依第五節判定嚴重度。

## 四、標準對照

緩解措施與 `NFR-*` 優先引用公認標準條目，閉環只維護「適用哪些章節」，不自行列舉安全項目。

**OWASP ASVS 5.0 全章對照**（驗證等級 = `asvs_level`）。每章歸入以下三種適用條件之一，不得有未歸屬的章節：

* **一律**：任何專案皆適用。
* **特徵**：依 `project.toml` 的 `[security]` 特徵判定。
* **技術**：使用該項技術時適用；使用者列於 `project.toml` 的 `tech_chapters_in_use`，未使用者須於 `not_applicable` 登錄。

| 章 | 名稱 | 適用條件 | 重點 |
| :---: | :--- | :--- | :--- |
| V1 | 編碼與淨化 | 一律 | 注入、輸出編碼 |
| V2 | 驗證與業務邏輯 | 一律 | 輸入驗證、業務規則不可繞過 |
| V3 | 網頁前端安全 | 特徵：`web_interface` | 跨來源、安全標頭、CSRF、點擊劫持 |
| V4 | API 與 Web 服務 | 特徵：`api_service` | 授權、資源消耗、輸入驗證 |
| V5 | 檔案處理 | 特徵：`processes_untrusted_files` | 檔案炸彈、路徑遍歷、類型偽裝 |
| V6 | 身分驗證 | 特徵：`multi_user`，或 `network_exposure` 為 `lan`／`internet` | 帳號、憑證、多因素驗證 |
| V7 | 工作階段管理 | 特徵：同 V6 | 工作階段建立、逾時、終止 |
| V8 | 授權 | 特徵：同 V6 | 功能與資源層級授權 |
| V9 | 自包含權杖 | 技術：使用 JWT 等自包含權杖 | 簽章驗證、有效期限、受眾 |
| V10 | OAuth 與 OIDC | 技術：使用第三方登入，或自建授權伺服器 | 授權流程、重新導向、權杖處理 |
| V11 | 密碼學 | 一律 | 雜湊、安全亂數、加密演算法、金鑰管理 |
| V12 | 安全通訊 | 特徵：`network_exposure` 為 `lan`／`internet`，或對外部服務發出連線 | 傳輸加密、TLS 憑證驗證（含服務對服務連線） |
| V13 | 組態 | 一律 | 設定安全、機密管理、相依元件 |
| V14 | 資料保護 | 特徵：`handles_pii` | 最小化、傳輸與儲存保護、保留期限 |
| V15 | 安全編碼與架構 | 一律 | 安全設計、相依元件風險 |
| V16 | 安全日誌與錯誤處理 | 一律 | 日誌不洩密、錯誤訊息不外露 |
| V17 | WebRTC | 技術：使用 WebRTC | 媒體與信令伺服器安全 |

**其他標準**（與 ASVS 並用）：

| 特徵 | 參照標準 | 重點 |
| :--- | :--- | :--- |
| `web_interface` | OWASP Top 10 | 常見網頁應用風險 |
| `api_service` | OWASP API Security Top 10 | 物件層級授權、資源消耗 |
| `uses_llm` | OWASP Top 10 for LLM Applications | 提示詞注入、敏感資訊外洩、過度授權、無上限消耗 |

* `[[security.not_applicable]]` 只登錄兩種情況，每筆附理由：技術條件章節未使用該技術；或特徵判定適用，但專案另有理由排除。依特徵已判定不適用者不必重複登錄。特徵改變時重新評估。
* ASVS 章節編號與名稱依 [OWASP ASVS 官方儲存庫](https://github.com/OWASP/ASVS) 5.0 版；新版發布時以規範變更更新本表。
* 本表由 `verify_doc_sync.py` 自動檢查：V1–V17 各一列、適用條件屬三類之一、技術章節皆已宣告、`not_applicable` 章節編號在範圍內。調整表格時保持「`| V<編號> | 名稱 | 適用條件 | 重點 |`」格式。

## 五、殘餘風險與延後規則

* Gate 1 威脅表的殘餘風險、Gate 2 與 QA 發現的安全問題，一律依 [bug-triage](../../bug-triage/SKILL.md) 嚴重度表判定 S1／S2／S3。
* **S1 不得延後**：於本次變更內修正，或立即依 `hotfix.md` 開缺陷處理。
* **S2／S3 延後**：Backlog 記錄嚴重度、判定理由與處理期限；不得只寫「不在本期範圍」。

## 六、自動化掃描

工具能抓的已知漏洞類別，交給 Gate 2 的 `security_scan.py`（靜態掃描與依賴漏洞掃描，工具與規則集設定於 `[security.tools]`），不在本框架人工列舉。

兩種掃描的觸發來源不同，因此分開觸發：程式碼變更觸發靜態掃描（只掃變更檔），需求檔變更觸發依賴漏洞掃描（只掃變更的需求檔）。為涵蓋「既有套件事後公布新漏洞」與「規則庫更新後未變更檔案未重掃」，超過設定天數自動執行完整掃描。

## 七、教訓回流

缺陷的逃逸分析須指出失效的是哪一層，並判定教訓歸屬：

| 失效層 | 範例 | 回寫位置 |
| :--- | :--- | :--- |
| 範圍宣告 | 應宣告「是」卻宣告「否」 | 第一節判定條件 |
| 威脅建模 | 漏畫邊界或漏問某類別 | 第三節邊界範例或六問 |
| 標準對照 | 章節誤標不適用 | 第四節對照或 `not_applicable` 理由 |
| 工具規則 | 掃描工具沒有對應規則 | `[security.tools]` 規則集或基準設定 |

* **通用**：任何專案都可能重演 → 開規範變更回寫本框架或工具設定，缺陷報告記錄該變更編號。
* **專案專屬**：只與本專案的領域或技術有關 → 回寫專案的檢核實例或 `project.toml`。
