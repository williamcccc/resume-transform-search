# 需求澄清規則 (Requirement Clarification)

> 本檔為 feature-design **階段 1.5** 之唯一正本。SKILL.md、角色檔與工具薄層只指向本檔，不重複規則。
> 適用功能開發軌 Step 1；缺陷修正軌不適用（「正確行為」由既有規格定義），升級轉功能開發時才適用。

代碼探測回答得了「怎麼做」，回答不了「為什麼做、做到哪裡算完成」。本階段把後者交還使用者決定，避免以猜測填滿 PRD。

---

## 一、時點

階段 1 代碼探測**之後**、階段 2 撰寫 PRD **之前**。能由程式碼、規範推得之事實，不得拿來問使用者。

## 二、觸發判定（命中任一條即須澄清）

| # | 條件 | 例 |
| :---: | :--- | :--- |
| 1 | 需求含未量化之形容詞或動詞，且未給目標值 | 「更好」「更準」「優化」「支援」「改善」 |
| 2 | 有兩種以上合理解讀，且不同解讀導致不同 AC | 「依年資篩選」是過濾還是排序 |
| 3 | 範圍邊界不明 | 是否包含某子功能；只改命令列或連 API 一起改 |
| 4 | 改變既有使用者可見行為 | 預設值、輸出格式、對外入口參數 |
| 5 | 品質評測範圍為「是」 | 門檻與標註資料來源屬業務決定 |
| 6 | 安全評估範圍為「是」，且有殘餘風險需人接受 | |
| 7 | 涉及刪除、覆寫既有資料或不可逆操作 | |

* 一條都未命中，方可略過本階段；PRD 假設清單仍須填寫並宣告「需求澄清：略過」。
* 本判定與 [arch_review_checklist.md](./arch_review_checklist.md) 之 Fast/Deep Track **正交**：是否澄清只看上表，不看架構衝擊大小。

## 三、提問方式

1. 只問影響範圍、AC 或門檻之事項，**每輪最多 5 題，原則一輪問完**。
2. 選擇題形式；每題附**建議選項（置首）與一句理由**，以及代碼探測查得之事實（檔案:行號），使用者不需自行翻程式碼。
3. 使用者可選「其他」自行填寫；回答「由 AI 決定」時採建議選項，記為「使用者授權」。
4. 多代理模式下，子 Agent 無法直接提問，亦不得自行代答：於本階段結束任務，回報中列出澄清問題（題目、選項、建議、查得事實），由主對話代問後新派工續行。各工具之提問介面見其薄層檔案。

## 四、撰寫 PRD 途中新浮現之問題

* **細節性**（不改範圍、AC 或門檻）：依建議選項處理，假設清單來源記為「使用者授權」，依據註明「待 Gate 1 追認」，於 Gate 1 一併呈現，不中斷使用者。
* **會推翻範圍者**：再問一輪（同第三節限制）。

## 五、假設清單（PRD 第 6 節）

格式正本為 [prd_template.md](./prd_template.md) 第 6 節。每條假設之來源限定以下五值：

| 來源 | 意義 |
| :--- | :--- |
| 程式碼 | 代碼探測查得，依據欄附檔案:行號 |
| 規範 | 專案規範或紅線，依據欄附文件連結 |
| 使用者原話 | 原始需求之字面內容 |
| 使用者確認 | 澄清問答之回答，依據欄附題號 |
| 使用者授權 | 使用者授權 AI 採建議選項，或途中細節待 Gate 1 追認 |

寫不出上述來源之假設，即須回本階段澄清；不得以「推測」列入。`verify_doc_sync.py` 自 `project.toml` 之 `docs.assumptions_enforced_from` 編號起強制檢查。
